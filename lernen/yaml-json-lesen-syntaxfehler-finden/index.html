YAML und JSON lesen und Fehler eingrenzen

Prüfungsrelevanz: hoch ≈ 25 Min. noch offen Pilot · fachlich in Prüfung

Ein Konfigurationsdokument kann fehlerfrei eingelesen werden und trotzdem das Falsche beschreiben. Du liest hier dieselben Daten in zwei Schreibweisen und prüfst zuerst die Struktur, dann die Anforderungen. Es werden keine echten Dienste verändert.

Nach dieser Einheit kannst du …

  • Verschachtelung und Datentypen in YAML und JSON lesen
  • Syntaxfehler von Vertragsverletzungen unterscheiden

1Vorwissen aktivieren

JSON enthält "aktiv": "false". Welchen Typ hat der Wert?

2Dieselben Daten, zwei Schreibweisen

JSON und YAML beschreiben strukturierte Daten, nicht von sich aus einen Programmablauf. Lies zuerst die Behälter, dann die Werte. JSON-Objekte enthalten benannte Werte; Arrays geordnete Elemente. YAML nennt diese Behälter Mapping und Sequenz.

Unser fiktiver Vertrag: dienst enthält name als Text, aktiv als Wahrheitswert und ports als Liste ganzer Zahlen. Die folgenden Dokumente beschreiben denselben Lernfall; sie sind keine fertige Compose-Konfiguration.

{
  "dienst": {
    "name": "lernserver",
    "aktiv": false,
    "ports": [8080, 8443]
  }
}

dienst:
  name: "lernserver"
  aktiv: false
  ports:
    - 8080
    - 8443

Schrittweise gelesen: An der Wurzel gibt es dienst. Darin liegen drei Schlüssel. ports enthält zwei Elemente; das zweite ist 8443. aktiv ist in beiden Beispielen ein Wahrheitswert. Die Reihenfolge der Listenelemente zählt; verlasse dich bei JSON-Objektschlüsseln nicht auf eine Reihenfolge.

3Schreibregeln gezielt prüfen

In JSON stehen Schlüssel und Texte in doppelten Anführungszeichen. Zwischen Einträgen steht ein Komma, nach dem letzten nicht. true, false und null werden kleingeschrieben. Kommentare sind nicht Teil der JSON-Grammatik. Nutze eindeutige Objektnamen: Doppelte Namen können von Empfängern unterschiedlich behandelt werden.

Im hier verwendeten YAML-Blockstil kennzeichnet Einrückung die Zuordnung. Verwende Leerzeichen, keine Tabs zur Einrückung. Zwei Leerzeichen pro Ebene sind unsere Konvention, keine allgemeine Pflichtzahl. - beginnt ein Listenelement, # kann einen Kommentar einleiten. Mit Anführungszeichen machst du Textwerte wie "false" ausdrücklich als Text kenntlich.

Wir verwenden YAML 1.2 mit Core-Schema. Parser-Version und Schema beeinflussen die Typauflösung; übertrage Regeln nicht ungeprüft auf ältere Werkzeuge. Die Beispiele verwenden deshalb klare Wahrheitswerte und ausdrücklich markierten Text.

4Fehler finden und reparieren

Sage zuerst voraus: Wird dieses JSON gelesen? Welche einzelne Stelle würdest du ändern?

{"dienst": {"aktiv": false,}}

Das Komma nach false kündigt einen weiteren Eintrag an, der fehlt. Entferne nur dieses Komma. Die reparierte Syntax lautet {"dienst": {"aktiv": false}}. Unser Vertrag ist damit noch nicht erfüllt: name und ports fehlen. Eine Syntaxreparatur ergänzt fehlende Anforderungen nicht automatisch.

Der Vertrag verlangt eine Zahl. Die Syntax "port": "8080" ist gültig. Was ist zu korrigieren?

Auch Einrückung kann die Bedeutung ändern, ohne die Syntax zu zerstören:

dienst:
  name: "lernserver"
aktiv: false

aktiv liegt hier neben dienst an der Wurzel, nicht darin. Wenn es zum Dienst gehören soll, rücke die Zeile wie name ein. Prüfe also den entstandenen Datenbaum, nicht nur die Meldung „gültiges YAML“.

Listeninhalt lesen

Die Liste ports lautet [8080, 8443, 9000]. Wie viele Elemente enthält sie?

5Systematisch statt auf Verdacht

Unser Prüfablauf: Dokument zunächst ohne Ausführung einlesen. Danach die erwarteten Schlüssel, Verschachtelungen und Typen vergleichen. Schließlich die beabsichtigte Wirkung in einer geeigneten Testumgebung prüfen. Ein erfolgreicher Parserlauf ist keine Deployment-Freigabe.

Eigenes JSON schreiben

Schreibe aus dem Gedächtnis ein JSON-Objekt mit name als Text, aktiv als Wahrheitswert false und ports als leerem Array. Erkläre, warum "false" und false nicht austauschbar sind.

0 Zeichen notiert
Muster: {"name":"test","aktiv":false,"ports":[]} enthält Text, Wahrheitswert und leeres Array. "false" wäre ein Text, false ist ein Wahrheitswert. Eine leere Liste ist syntaktisch gültig; ob sie erlaubt ist, legt der Vertrag fest. Der Vergleich ist eine Selbstprüfung, kein Parser für deine Eingabe.

8Quellen und Grenzen

Primärquellen: RFC 8259, Abschnitte 2–7 und YAML 1.2.2, insbesondere 6.1 und 10.3.2, ausgewählte Abschnitte am 17.09.2026 gelesen. Eigene Aufgaben und Grafiken. Die automatischen Buchtreffer waren fachlich unpassend und wurden nicht übernommen.

Kein vollständiger YAML-Kurs: Tags, Aliase und mehrzeilige Skalare bleiben außerhalb dieser Einheit. Übungen führen keine Konfiguration aus. Der Schreibauftrag wird durch Selbstvergleich geprüft, nicht automatisch auf Syntax analysiert.
