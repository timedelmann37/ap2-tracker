Windows Server und Active Directory: Struktur, DNS, Redundanz

Prüfungsrelevanz: hoch ≈ 35 Min. noch offen Pilot · fachlich in Prüfung

Die Werkstatt Kranich betreibt eine AD-Domäne für zwei Standorte. In Berlin fällt ein Server aus; gleichzeitig können einige Clients keinen Domain Controller finden. Wo liegt die Ursache: in der OU, im Standort, im DNS oder bei fehlender Redundanz? Du trennst zuerst die Begriffe und leitest dann einen überprüfbaren Ausfallplan ab.

Nach dieser Einheit kannst du …

  • Rolle/Feature und Forest, Domain, OU, Site im Szenario richtig unterscheiden
  • DNS-Abhängigkeit und DC-Redundanz mit konkreten Prüfungen begründen

11 · Welche Schicht ist gemeint?

Kranich will Benutzerkonten zentral verwalten. Was wird dazu auf einem Windows Server eingerichtet?

Eine Serverrolle beschreibt eine Hauptaufgabe des Servers. Für eine Windows-Domäne installierst du die Rolle Active Directory Domain Services (AD DS) und konfigurierst anschließend den Server als Domain Controller (DC). Features ergänzen Funktionen; sie sind nicht dasselbe wie Forest, Domäne oder OU. Die Rollen-/Feature-Auswahl ist ein Installationsschritt, noch kein Nachweis, dass Anmeldung, DNS und Replikation funktionieren.

Kranich legt eine AD-Gesamtstruktur an. Der Forest ist die oberste logische Grenze mit gemeinsamem Schema und Konfiguration. Darin liegt die Domäne ad.kranich.example: Sie enthält unter anderem Benutzer, Computer und Gruppen; ihre DCs halten die Domänendaten und authentisieren. Innerhalb der Domäne ordnet die OU Werkstatt Benutzer und Geräte für delegierte Verwaltung und spätere Richtlinien. Eine OU ist keine neue Domäne und keine eigene physische Niederlassung.

Kranich eröffnet einen zweiten Standort mit eigenem IP-Subnetz. Für eine standortnahe DC-Auswahl und Replikationswege wird vor allem was modelliert?

22 · DNS finden, DC erreichen

Im Fall gibt es Berlin (192.0.2.0/24) und Leipzig (198.51.100.0/24) als Sites. In der einzigen Domäne ad.kranich.example läuft je ein beschreibbarer DC: DC-BER und DC-LEI. Die Sites gruppieren die jeweiligen Subnetze, damit Clients passende DCs finden und die Replikation über die Verbindung geplant werden kann. Das ist eine andere Perspektive als die OU-Struktur.

Ein Domänenclient sucht einen DC nicht durch Raten seiner IP-Adresse: Die DNS-basierte DC-Suche fragt nach SRV-Einträgen für AD-Dienste, löst anschließend Zielnamen auf und prüft erreichbare Kandidaten. Für eine LDAP-Suche ist _ldap._tcp.ad.kranich.example ein anschaulicher Abfragebegriff. Wenn DNS fehlschlägt, hilft ein gesunder zweiter DC dem Client beim Auffinden zunächst nicht. Andersherum kann ein korrekter DNS-Eintrag auf einen nicht erreichbaren DC zeigen. Beobachtung und Test müssen diese Fehler trennen.

DC-BER ist ausgefallen. DC-LEI läuft, aber die Berliner Clients nutzen ausschließlich den ebenfalls ausgefallenen DNS-Dienst auf DC-BER. Was prüfst du zuerst?

Störung begründen

Kranich meldet: „Der zweite DC ist doch da – warum klappt die Anmeldung nicht?“ Erkläre in mindestens drei Sätzen die Prüfkette vom Client bis zum DC. Unterscheide einen DNS-Fehler von einem DC-/Replikationsfehler.

0 Zeichen notiert
Muster: Zuerst prüfe ich, welche DNS-Server der Client tatsächlich nutzt und ob ein erreichbarer DNS-Dienst die AD-SRV- und Zieladressdatensätze liefert. Danach prüfe ich, ob der gefundene DC erreichbar ist und ob der Client einer passenden Site zugeordnet ist. Zuletzt prüfe ich die Gesundheit der DCs, insbesondere Replikation und SYSVOL. Ein zweiter DC allein hilft nicht, wenn der einzige eingetragene DNS-Dienst ausfällt; korrekte DNS-Antworten allein beweisen umgekehrt noch keine gesunde Anmeldung.

33 · Redundanz ist ein geprüfter Betriebszustand

Zwei DCs in derselben Domäne können einen einzelnen DC-Ausfall abfedern: Domänendaten werden zwischen ihnen repliziert, und der Client kann einen erreichbaren DC auswählen. Dazu braucht Kranich aber die passenden Voraussetzungen: erreichbare DNS-Dienste mit korrekten Einträgen, erreichbare Netzwege, sinnvolle Site-/Subnetz-Zuordnung und eine überwachte Replikation. Wenn ein Standort bei WAN-Ausfall weiter lokal anmelden können muss, gehört auch diese Anforderung in die Platzierungsentscheidung.

Ein DC ist kein passiver Klon, der nur bei Fehlern eingeschaltet wird. Ebenso ist „zwei DCs vorhanden“ noch kein Restore-Konzept. Kranich plant ein separates, getestetes Wiederherstellungsverfahren und prüft bei einer Störung die tatsächlichen Symptome: Kann ein Client die SRV-Einträge abfragen? Welchen DC wählt er? Erreichen Anmeldungen beide DCs? Werden Änderungen repliziert? Sind die Richtliniendateien in SYSVOL verfügbar? Diese Prüfungen machen aus einer Architekturzeichnung einen belastbaren Betriebsnachweis.

Prüfauftrag: Formuliere bei jeder Architekturentscheidung Annahme → erwarteter Nutzen → prüfbarer Test. Beispiel: „DC-LEI ist für Berliner Clients erreichbar → bei Ausfall von DC-BER ist eine Domänenanmeldung möglich → Ausfall in einer Testumgebung simulieren, DNS-Suche und Anmeldung protokollieren.“ Das Ergebnis hängt von Netz, DNS und Clientzustand ab; eine pauschale Garantie wäre falsch.
