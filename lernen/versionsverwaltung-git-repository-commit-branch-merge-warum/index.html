Repository, Commit, Branch und Merge unterscheiden und den tatsächlich gesicherten Skriptstand bestimmen. Du bearbeitest eigene Papierfälle; es werden keine echten Systeme verändert.

Nach dieser Einheit kannst du …

  • Arbeitsstand, Staging und Commit korrekt unterscheiden
  • Zusammenführung von Branches fachlich prüfen

1Vorwissen aktivieren

Du speicherst eine Datei im Editor. Ist damit schon ein Git-Commit entstanden?

2Drei Orte statt einer Dateikopie

Ein Repository enthält versionierte Projektstände und ihre Historie. Ein Commit benennt einen gespeicherten Snapshot mit Metadaten und Vorgängern. Im Arbeitsverzeichnis bearbeitest du Dateien. Der Index, oft Staging-Bereich genannt, hält den für den nächsten Commit ausgewählten Stand.

git add bericht.ps1 übernimmt den aktuellen Inhalt dieser Datei in den Index. git commit sichert den Index. Spätere Bearbeitungen werden nicht automatisch mitgenommen. git status unterscheidet vorgemerkte, nicht vorgemerkte und unversionierte Änderungen. git diff zeigt Änderungen zwischen Arbeitsdatei und Index; git diff --cached zwischen Index und letztem Commit.

3Den gesicherten Inhalt vorhersagen

Eigener Papierfall: Im letzten Commit steht grenze = 5. Du änderst auf 8 und führst git add aus. Danach änderst du auf 12, ohne erneut vorzumerken. Sage zuerst voraus: Welche Zahl wird beim folgenden Commit gesichert?

Ort vor dem Commit Wert
Letzter Commit 5
Index 8
Arbeitsdatei 12

Der Commit erhält 8, weil dies der vorgemerkte Stand ist. Die Arbeitsdatei bleibt bei 12; diese spätere Änderung bleibt uncommitted. Für 12 müsstest du erneut gezielt vormerken und prüfen.

Neuer Staging-Fall

Letzter Commit: 3. Auf 6 geändert und vorgemerkt. Danach auf 9 geändert, nicht erneut vorgemerkt. Welcher Wert landet im normalen Commit?

4Branch und Merge

Ein Branch ist ein beweglicher Verweis auf einen Commit, keine vollständige unabhängige Ordnerkopie. Neue Commits entwickeln den aktuellen Branch weiter. Ein Merge führt Historien zusammen. Bei einem Fast-forward wird der Zielverweis vorgeschoben; bei auseinanderentwickelten Historien kann ein Merge-Commit entstehen.

Eigener Fall: main erhöht eine Wartezeit, ein zweiter Branch ergänzt eine Eingabeprüfung. Git kann die Texte möglicherweise automatisch zusammenführen. Ob beide Änderungen zusammen richtig funktionieren, entscheidet ein Test. Bearbeiten beide dieselbe Stelle unterschiedlich, kann ein Konflikt entstehen. Dann die beabsichtigte Gesamtfunktion klären, Ergebnis bearbeiten, prüfen und erst danach den Merge abschließen.

Git meldet eine konfliktfreie Zusammenführung. Was ist damit belegt?

5Warum auch kleine Skripte?

Änderungsgrund und betroffene Dateien gehören zusammen in einen überschaubaren Commit. So lässt sich später erklären, welche Prüfregel wann geändert wurde. Ein lokaler Commit ist noch kein Push und ein Push noch kein erfolgreicher Betrieb. Versionsverwaltung ersetzt keine Datensicherung. Zugangsdaten gehören nicht in die Historie.

Ein Branch für einen Versuch schützt nicht vor allen Fehlern: Vor dem Wechsel ungesicherte Änderungen prüfen. Diese Einheit führt keine Git-Befehle aus und beschreibt keine Lösch- oder Zurücksetzroutine.
