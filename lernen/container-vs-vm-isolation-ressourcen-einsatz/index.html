Container oder VM? Die Grenze liegt beim Kernel

Ein Container ist keine „kleine VM“. Beide verpacken Workloads, aber sie ziehen die Isolationsgrenze an verschiedenen Stellen. Die wichtigste Frage lautet: Teilen die Workloads denselben Kernel, oder besitzt jeder Gast einen eigenen?

Nach dieser Einheit kannst du …

  • Prozessisolierten Container und VM nach gemeinsamem beziehungsweise eigenem Kernel abgrenzen
  • Ressourcen-, Start- und Sicherheitsanforderungen für Container, VM oder Kombination begründet abwägen

1Die Kernelfrage stellen

Auf einem Linux-Host laufen drei prozessisolierte Container. Wie viele eigenständige Gast-Kernel enthalten diese drei Container?

2Zwei Schichtenmodelle lesen

Ein prozessisolierter Container ist ein isolierter Anwendungsprozess mit den benötigten Dateien und Bibliotheken aus einem Image. Sein Kernel kommt vom Host. Isolation entsteht unter anderem durch getrennte Prozess-, Netzwerk- und Dateisystemsichten sowie Ressourcenbegrenzung. Das Image ist nicht die laufende Instanz: Erst beim Start entsteht ein Container.

Eine VM erhält virtuelle Hardware und startet ein vollständiges Gastbetriebssystem mit eigenem Kernel. Das schafft eine andere, im Regelfall stärkere Trennungsgrenze und erlaubt unterschiedliche Gastbetriebssysteme, benötigt aber die Ressourcen der Gäste. Ein Container kann leichter sein und typischerweise schneller starten, weil kein eigenes Gast-OS bootet. Das ist kein Messwertversprechen: ein kaltes Image, Initialisierung oder Netzwerk-/Speicherzugriff können den Start dominieren. Eine kleine VM kann für bestimmte Lasten geeigneter sein als ein schlecht konfigurierter Container.

Die Anwendung läuft als Linux-Container auf einem Windows-Laptop. Widerlegt das die Aussage „Container teilen einen Kernel“?

3Startzeit und Schutzbedarf abwägen

Fall A – gleichartige Webdienste: Fünf kleine Dienste sollen regelmäßig neu gebaut und verteilt werden; der Host-Kernel passt zu allen. Container sind ein guter Kandidat für reproduzierbare Anwendungsumgebungen. Prüfe Image-Herkunft, Updates, Ressourcenlimits, Datenhaltung und Netzwerkrechte.

Fall B – anderer Kernel oder starke Mandantentrennung: Eine Anwendung benötigt ein eigenes Gastbetriebssystem; ein zweiter Workload stammt von einer nicht vertrauenswürdigen Partei. VMs sind als getrennte Gastumgebungen ein geeigneter Ausgangspunkt. Ein bloßer Container teilt den Host-Kernel; Fehlkonfiguration, privilegierte Rechte oder Kernel-Schwachstellen können diese Grenze schwächen.

Fall C – kombinieren: Mehrere Container laufen in einer VM. So lassen sich Anwendungsbereitstellung und eine zusätzliche VM-Grenze kombinieren. Windows bietet außerdem Hyper-V-isolierte Container, bei denen jeder Container in einer optimierten VM mit eigenem Kernel läuft. Deshalb muss bei konkreten Produkten der Isolationsmodus mitgenannt werden. Keine Variante ersetzt Backups, Patches oder Zugriffsregeln.

Prozessisolierte Container teilen den Host-Kernel, während jede VM ein Gastbetriebssystem mit eigenem Kernel ausführt. Container können deshalb weniger Gast-OS-Ressourcen benötigen und oft schneller starten; feste Zeit- oder Sicherheitsgarantien folgen daraus nicht.
