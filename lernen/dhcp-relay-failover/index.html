DHCP über Netzgrenzen verfügbar planen

Prüfungsrelevanz: hoch ≈ 24 Min. noch offen Pilot · fachlich in Prüfung

DHCP-Relay und DHCP-Redundanz lösen zwei verschiedene Probleme. Ein Relay überbrückt die Routergrenze für Clientanfragen. Redundanz entscheidet dagegen, welcher Server bei Last oder Ausfall gültige Leases vergeben kann. Erst wenn beide Ebenen getrennt geplant sind, ist die Adressvergabe wirklich belastbar.

Nach dieser Einheit kannst du …

  • einen DHCP-Relay am passenden Routerinterface platzieren und die Auswahl des entfernten Scopes erklären
  • Split Scope und zustandssynchronisiertes DHCP-Failover anhand von Lease-Zustand und Ausfallverhalten unterscheiden

1Einstieg: Welches Problem wird gelöst?

Clients in VLAN 20 erreichen den zentralen DHCP-Server hinter einem Router nicht, während Clients im Servernetz funktionieren. Welche Maßnahme adressiert zuerst genau diese Netzgrenze?

Zwei Achsen

Relay = Erreichbarkeit über Subnetzgrenzen. Redundanz = gültige Vergabe bei Last oder Serverausfall. Ein Netz kann das eine benötigen, ohne dass das andere damit automatisch gelöst ist.

2Relaypfad und Scope-Auswahl

Ein unkonfigurierter Client sendet seine erste DHCP-Anfrage lokal. Der Router leitet diesen Broadcast nicht wie normalen Unicastverkehr weiter. Ein Relay-Agent am Interface des Clientnetzes nimmt die Anfrage auf und sendet sie gezielt an einen oder mehrere konfigurierte DHCP-Server.

Dabei liefert der Relaypfad dem Server Information darüber, aus welchem Clientnetz die Anfrage stammt. Der Server kann dadurch den Scope für genau dieses Subnetz auswählen. Ein erreichbarer Server ohne passenden Scope kann dem Client keine passende Adresse anbieten.

Der Server erhält über einen Relay eine Anfrage aus 192.168.30.0/24. Er besitzt nur einen Scope für 192.168.20.0/24. Was ist die stärkste Diagnose?

3Geführte Übung: drei VLANs anbinden

Planungsschritte sortieren

Ein zentraler DHCP-Dienst soll Clients in drei gerouteten VLANs versorgen. Bringe die Schritte in eine prüfbare Reihenfolge.

Übung
  1. 1Clientsubnetze, Routerinterfaces und benötigte DHCP-Optionen vollständig erfassen.
  2. 2Für jedes Clientsubnetz einen konfliktfreien Scope auf dem Server anlegen.
  3. 3Relay an jedem relevanten Clientinterface mit den autorisierten Serverzielen konfigurieren.
  4. 4DORA, Scope-Auswahl, Optionen, Rückweg sowie Verhalten bei Serverausfall je VLAN testen.

4Split Scope und Failover sauber trennen

Beim Split Scope erhält Server A beispielsweise einen nicht überlappenden Teil des Pools und Server B den anderen. Beide können Clients erreichen, führen aber keine gemeinsame Lease-Datenbank. Fällt A aus, bleiben nur die noch freien Adressen im Teil von B unmittelbar verfügbar. Reservierungen und Optionen müssen konsistent auf beiden Servern gepflegt werden.

Bei zustandssynchronisiertem Failover tauschen Partner Lease-Informationen aus. Im Active-Passive-Modell vergibt normalerweise ein Server, während der Partner den Zustand übernimmt. In einem lastverteilenden Failover-Modus beantworten beide Server Anfragen nach den Regeln ihrer Implementierung und können bei Ausfall die Zuständigkeit erweitern. Das ist nicht bloß Split Scope: Der gemeinsame Zustand ist das entscheidende Merkmal.

Produktgrenzen dokumentieren

Bei DHCPv4 darfst du keinen herstellerübergreifenden Failover-Verbund voraussetzen. Prüfe unterstützte Partner, Zustände, Timer, Kommunikationspfad und das Verhalten bei Netztrennung anhand der eingesetzten Implementierung.

5Beispiel: Ausfall richtig bewerten

Ein /24-Clientnetz nutzt Split Scope: Server A vergibt .50 bis .169, Server B .170 bis .219. Es gibt keinen Zustandsabgleich. Fällt A aus, ist B zwar weiter erreichbar, kann aber nicht einfach freie Adressen aus dem Bereich von A übernehmen. Die verfügbare Neukundenkapazität beschränkt sich auf Bs eigene noch freie Leases.

In einem kompatiblen Failover-Verbund könnten beide Partner den Lease-Zustand synchronisieren. Ob und wann B nach einem Fehler zusätzliche Zuständigkeit übernimmt, folgt jedoch dem konfigurierten Modus und dessen Timern. „Zweiter Server vorhanden“ ist deshalb noch kein ausreichender Verfügbarkeitsnachweis.

0 Zeichen notiert
Muster: Der lokale Broadcast erreicht das Routerinterface des Client-VLANs. Der dortige Relay-Agent leitet die Anfrage an konfigurierte Server weiter und liefert den Subnetzkontext, damit der passende Scope gewählt wird. Split Scope nutzt getrennte Pools ohne gemeinsamen Lease-Zustand; beim Ausfall bleibt nur der andere Pool. Failover repliziert Lease-Zustand und übernimmt nach produktabhängigen Rollen und Timern.
