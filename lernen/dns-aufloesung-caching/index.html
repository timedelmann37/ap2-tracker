DNS-Auflösung und Caching nachvollziehen

Prüfungsrelevanz: hoch ≈ 24 Min. noch offen Pilot · fachlich in Prüfung

Der Client fragt normalerweise nicht selbst Root-, TLD- und autoritative Server ab. Sein Stub-Resolver übergibt die Aufgabe an einen rekursiven Resolver. Dieser liefert entweder eine gecachte Antwort oder verfolgt die Delegationen der DNS-Hierarchie. Wer diese Rollen trennt, kann Auflösungsfehler gezielt lokalisieren und versteht, warum eine DNS-Änderung nicht überall sofort sichtbar wird.

Nach dieser Einheit kannst du …

  • Stub-Resolver, rekursiven Resolver, Forwarder und autoritative Server in einer Namensauflösung korrekt zuordnen
  • Caching und TTL bewerten sowie Forward Lookup und Reverse Lookup voneinander unterscheiden

1Einstieg: Wer erledigt die Arbeit?

Ein Notebook fragt seinen konfigurierten DNS-Server nach www.example.org. Welche Rolle übernimmt dieser Server typischerweise für den Client?

Zwei Gesprächsarten

Der Client bittet rekursiv um das Endergebnis. Der Resolver folgt bei Bedarf iterativ den Verweisen der DNS-Hierarchie.

2Rollen in der Auflösung

Ein Stub-Resolver im Endgerät besitzt nur begrenzte Auflösungslogik und fragt den eingestellten DNS-Dienst. Ein rekursiver Resolver übernimmt die vollständige Auflösung und betreibt einen Cache. Ein Forwarder ist ein festgelegter nächster DNS-Server, an den ein Server nicht lokal beantwortbare Anfragen weitergibt. Autoritative Server liefern verbindliche Daten für ihre Zonen; Root- und TLD-Server liefern dabei meist Delegationsinformationen statt der gesuchten Hostadresse.

Cache-Miss durchspielen

Ordne den vereinfachten Ablauf einer noch nicht gecachten Auflösung.

Übung
  1. 1Der zuständige autoritative Server liefert den angefragten Datensatz.
  2. 2Der Stub-Resolver sendet die Anfrage an seinen rekursiven Resolver.
  3. 3Der Resolver speichert die Antwort mit TTL und liefert sie zurück.
  4. 4Der Resolver folgt den Verweisen von Root und TLD zur Zielzone.

3Cache, TTL und Änderungen

Die TTL eines Resource Records gibt an, wie lange ein Cache diesen Datensatz verwenden darf. Ein hoher Wert reduziert Abfragen, kann geplante Änderungen aber länger sichtbar verzögern. Ein niedriger Wert erhöht die Abfragelast, ermöglicht nach Ablauf bestehender Cacheeinträge jedoch schnellere Aktualisierung. Vor einer geplanten Umstellung wird die TTL deshalb rechtzeitig gesenkt und danach wieder auf einen passenden Betriebswert erhöht. Bereits gecachte Restlaufzeiten verschwinden dadurch nicht rückwirkend.

Ein A-Record wurde geändert, ein Resolver besitzt aber noch den alten Datensatz mit 900 Sekunden Rest-TTL. Was ist die beste Erklärung?

4Forward und Reverse Lookup

Beim Forward Lookup startet die Frage mit einem Namen und sucht beispielsweise über A oder AAAA eine Adresse. Beim Reverse Lookup startet sie mit einer IP-Adresse und fragt einen PTR-Record in der umgekehrten Namensstruktur ab. Ein PTR-Record wird in der zuständigen Reverse-Zone gepflegt; er entsteht nicht automatisch aus einem A- oder AAAA-Record. Reverse DNS ersetzt außerdem keine Identitäts- oder Vertrauensprüfung.

Richtung benennen

Name → Adresse ist Forward Lookup. Adresse → Name ist Reverse Lookup. Die Rückrichtung ist ein eigener DNS-Datensatz, keine automatische Umkehrfunktion.
